# 功能热插拔方案设计

> 目标：把「便利贴、任务清单、以及未来的功能」改造为**用户按需开启 / 手动装载**的热插拔模块，并**降低内存与 CPU 占用**。
> 状态：设计稿（未实施），供评审。

---

## 1. 现状分析：为什么现在做不到"热插拔"

当前所有功能都**硬编码**在宿主里，具体耦合点：

| 位置 | 耦合内容 |
| --- | --- |
| `App.xaml.cs` | `CreateNote/OpenNote/DeleteNote`、`CreateTaskList/OpenTaskList/...` 全部硬编码；启动时直接 `NoteStore.Load()` 装载**全部**数据 |
| `Models/StickyNoteModel` / `TaskListModel` | 模型直接放在宿主，`NoteStore` 把便利贴和任务清单**混存在一个 notes.json** |
| `MainWindow.xaml.cs` | 左侧导航 `NavNotes`/`NavTasks`、搜索/排序/视图状态字段（`_searchNoteText`/`_sortTaskTag`/...）按功能硬编码；数据模板硬编码 |
| `TrayIconService.cs` | 托盘菜单"新建便利贴/新建任务清单"硬编码 |
| `SettingsWindow` / `DefaultAppearanceWindow` | 默认外观按"便利贴/任务清单"硬编码两套 |

**资源占用现状（要降低的目标）**：

- **内存**：启动即装载全部数据（notes.json 整体反序列化）+ 创建全部 `IsOpen=true` 的窗口；每个 WPF Window、`ObservableCollection`、背景 `ImageBrush` 都常驻内存。
- **CPU**：每个开启"悬停显示"的窗口有一个 **120ms 的 `DispatcherTimer` 轮询全局鼠标坐标**（`GetCursorPos` + 命中判断），常驻唤醒；禁用类目后这些开销也不会消失。

---

## 2. 需求定义

1. **功能级粒度**：便利贴、任务清单（以及未来的功能，如番茄钟、备忘录、日历等）各自是一个"功能模块"。
2. **启用 / 禁用**：用户在设置里开关某个功能；禁用后其窗口全部关闭、数据保留但**不装载**、托盘/管理界面入口消失。
3. **按需装载**：默认只启用用户勾选的功能，其余模块**代码不实例化、数据不读盘、UI 不生成**。
4. **资源目标**：
   - 禁用功能后：内存增量 ≈ 0（理想：程序集根本不加载），无任何定时器/轮询；
   - CPU 空闲占用接近 0（消灭常驻轮询）。

---

## 3. 方案对比

| 方案 | 思路 | 内存收益 | CPU 收益 | 复杂度 | 风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 单进程模块化 + 延迟激活**（"软热插拔"） | 功能拆成模块，启用时才实例化/读数据/建窗口；禁用时反向清理 | ★★★★ | ★★★★ | 低 | 低 | **推荐第一阶段** |
| **B. 可卸载程序集（Collectible AssemblyLoadContext）** | 每个功能编译为独立 DLL，启用时加载入独立 ALC，禁用时 `Unload()` | ★★★★★ | ★★★★ | 高 | **高（WPF 强引用极易泄漏导致卸载失败）** | 可选第二阶段，仅对无 UI 的重逻辑做 |
| **C. 子进程隔离** | 每个功能一个子进程 exe，宿主通过命名管道 IPC 通信，退出即彻底释放 | ★★★★★ | ★★★★★ | 高 | 中 | 可选第三阶段，面向未来重型功能 |
| **D. MEF（System.Composition）** | 用 `[Export]`/`[Import]` 做组合式插件发现 | ★★★（Lazy import） | ★★★ | 中 | 低 | 可作为 A 的实现手段之一，非必需 |
| **E. MAF（System.AddIn）** | 微软老插件框架 | — | — | — | 已过时，仅 .NET Framework | 淘汰 |

**关键判断**：

- 本项目是**单 EXE、小体量的 WPF 应用**。便利贴/任务清单本身的程序集代码量很小（几百 KB），"不加载程序集"省不了几 MB；**真正吃内存的是数据、窗口和图片资源，吃 CPU 的是轮询定时器**——这些用方案 A 就能全部解决，且不引入进程/IPC/卸载泄漏的复杂度。
- B 的陷阱：WPF 的样式、绑定、模板解析器会长期持有类型引用，`ALC.Unload()` 在含 UI 的程序集上**大概率卸不掉**（`AssemblyLoadContext` 长期为 Loading 状态），收益为零还留坑。
- C 适合"个别功能确实很重"（如内置浏览器、AI 助手）时**单独**上，不适合把便利贴这种轻功能拆出去（WPF 子进程每实例基线内存 ~60MB，反而更费）。

**推荐路线：A 为地基（必做），D 视需要引入，C 留给未来重型功能，B 基本放弃。**

## 4. 推荐方案详细设计（方案 A：模块化 + 延迟激活）

### 4.1 总体架构

```
StickyNote.exe（宿主）
├── Host（宿主内核）
│   ├── FeatureHost            # 模块生命周期：Activate / Deactivate
│   ├── FeatureRegistry        # 已安装模块清单（清单文件驱动）
│   ├── FeatureStore           # 每个模块独立的启用状态 + 数据文件
│   ├── 扩展点聚合器            # 管理“模块往宿主 UI 注入什么”
│   └── 基础服务：托盘、全局热键、日志、AppSettings
└── Modules（类库引用，非运行时加载）
    ├── NotesModule        # 便利贴：实现 IFeatureModule
    ├── TaskListModule    # 任务清单：实现 IFeatureModule
    └── (未来功能...)
```

> 与 B/C 的关系：模块以**普通项目引用**编译进主程序（不丢单文件发布的优势）；`IFeatureModule` 的实例只在用户启用时创建。将来若某个模块需要真卸载/独立进程，只需替换它接入宿主的方式，**接口不变**。

### 4.2 核心接口

```csharp
/// <summary>功能模块契约。宿主只认识这个接口，不认识任何具体功能。</summary>
public interface IFeatureModule
{
    /// <summary>模块唯一 ID，如 "notes"、"tasklist"（用于数据文件、设置项命名）</summary>
    string Id { get; }

    /// <summary>显示名与图标（管理界面导航、托盘菜单用）</summary>
    string DisplayName { get; }
    string Icon { get; }

    /// <summary>激活：读数据、注册 UI 入口、恢复窗口。禁用状态 → 启用状态时调用。</summary>
    Task ActivateAsync(IFeatureContext context);

    /// <summary>停用：关闭全部窗口、清空内存数据、注销 UI 入口。启用状态 → 禁用状态时调用。</summary>
    Task DeactivateAsync();

    /// <summary>当前是否处于激活态</summary>
    bool IsActive { get; }
}

/// <summary>宿主提供给模块的环境（依赖倒置，模块不直接 new 全局对象）</summary>
public interface IFeatureContext
{
    // 数据：每个模块一个独立文件，如 notes__notes.json、tasklist__lists.json
    Task<T?> LoadDataAsync<T>();
    Task SaveDataAsync<T>(T data);

    // UI 扩展点（见 4.4）
    INavigationSection Navigation { get; }   // 管理界面左侧导航
    ITrayMenuSection TrayMenu { get; }       // 托盘菜单
    IGlobalSettingsSection Settings { get; } // 全局设置页
    INewItemSection NewItem { get; }         // 「＋ 新建」动作

    // 宿主基础服务
    void ShowBalloon(string title, string message);
    void RegisterTopmostTarget(Window w);   // 统一置顶管理
}
```

### 4.3 生命周期与数据

**激活 / 停用流程：**

```
用户在「设置 → 功能管理」中打开开关
  → FeatureHost.Activate(id)
      → new XxxModule()                      # 首次实例化（此前类型从未构造）
      → ActivateAsync(ctx)
          → LoadDataAsync()：仅读该模块的数据文件（懒装载，见下）
          → Navigation.Register(...)：左侧导航出现该类目
          → TrayMenu.Register(...)：托盘菜单出现「新建 xx」
          → 恢复 IsOpen 的窗口
```

```
用户关闭开关（弹确认：将关闭 N 个窗口）
  → FeatureHost.Deactivate(id)
      → DeactivateAsync()
          → Close() 所有窗口（内存随之释放）
          → 数据已实时落盘（现有 SaveAll 机制平移进模块）
          → 注销导航 / 托盘 / 新建入口
      → 引用置 null → GC 可回收窗口、ObservableCollection、ImageBrush
```

**数据文件拆分（模块隔离的前提）：**

```
%LOCALAPPDATA%\StickyNoteWPF\
├── settings.json          # 宿主设置 + enabled_features 列表
├── features\notes\notes.json        # 仅便利贴
└── features\tasklist\lists.json     # 仅任务清单
```

- 启动时**只反序列化启用模块的数据**——禁用的功能数据留在磁盘上不占内存；
- 迁移：首次运行检测旧 `notes.json`，按模块拆分到各自目录，旧文件改名 `.migrated.bak`；
- 各模块数据的损坏备份/防覆盖逻辑（现有 `NoteStore` 的优点）下沉为 `FeatureStore` 的通用能力，所有模块免费获得。

### 4.4 UI 扩展点（解耦硬编码）

当前 `MainWindow` 的导航、搜索状态、卡片模板全部按"便利贴/任务清单"写死，改为**注册制**：

```csharp
public interface INavigationSection
{
    // 模块注册一个分类页：图标、标题、以及该页的内容提供者
    IDisposable Register(NavEntry entry);
}

public class NavEntry
{
    public string Icon { get; init; }         // "📝"
    public string Title { get; init; }         // "便利贴"
    public Func<FrameworkElement> CreateContent { get; init; } // 卡片列表控件（模块自带 DataTemplate）
    public ISearchable? Searchable { get; init; }  // 搜索/排序挂接点
}
```

- 现有"每个类目独立记忆搜索/排序/视图"的设计**原样下放**给各模块页自己持有（本来就是按类目隔离的状态），宿主只管导航容器；
- 托盘菜单 / 「＋ 新建」按钮同理：菜单项由激活模块注册，禁用后消失；
- `DefaultAppearanceWindow` 的"按类型独立"结构不变，只是入口由模块注册。

### 4.5 资源优化专项（与热插拔并行，独立可先行）

这部分**即使不做热插拔也值得立刻做**，是降 CPU/内存收益最大的地方：

**CPU——消灭 120ms 轮询：**

| 现状 | 改法 |
| --- | --- |
| 每个悬停窗口一个 `DispatcherTimer`，120ms 全量轮询 `GetCursorPos` + 逐窗口矩形判断 | 宿主持有**一个**低频全局钩子（`SetWindowsHookEx` WH_MOUSE_LL，或退而求其次：单一定时器 + 事件广播），鼠标位置变化时一次计算、分发给所有注册了悬停区的窗口 |
| 悬停关闭时窗口 `Opacity=0` 但视觉树仍在渲染 | `Hide()`（真正停渲染）代替 `Opacity=0`（当前为了坐标命中保留可见性，改钩子方案后不再需要） |

效果：N 个悬停窗口从 **N 个定时器（每秒 ~8.3×N 次唤醒+P/Invoke）** 降为 **0 常驻**（钩子仅在有鼠标消息时触发）。

**内存：**

- 背景图片：`ImageBrush` 引用的 `BitmapImage` 全部常驻。改为模块级 `FrozenBitmapCache`：同一图片共享一份解码位图；窗口关闭时释放；可选降采样（按窗口实际尺寸 Decode）；
- 未激活模块：数据不读、窗口不建（前述懒装载已覆盖）；
- 单文件发布不受影响（Trimmed 模式下需给模块类型加 `DynamicallyAccessedMembers` 标注或直接硬引用模块类型——当前 `Program` 为静态引用，天然安全）。

### 4.6 用户交互设计

- **入口**：全局设置新增「**功能管理**」页：每个已安装功能一行（图标 + 名称 + 开关 + 简介），禁用行显示"已禁用 · 数据保留"；
- **首启默认**：便利贴开启、任务清单开启（与现状一致，不打扰老用户）；
- **数据安全**：禁用 ≠ 删除；彻底删除数据需要显式二次操作（先禁用，再在功能管理里点"清除数据"）。

## 5. 实施路线（建议三阶段，可独立交付）

| 阶段 | 内容 | 收益 | 工作量估计 |
| --- | --- | --- | --- |
| **0. 资源优化（先行独立）** | 鼠标轮询 → 全局钩子单点分发；`Opacity=0` → `Hide()`；位图共享/释放 | CPU 空闲占用大幅下降（无需等热插拔） | 小 |
| **1. 模块化重构（软热插拔）** | `IFeatureModule` + `FeatureHost/FeatureStore` + 数据文件拆分 + 导航/托盘/新建扩展点 + 设置页功能开关 | 用户可启用/禁用功能；禁用功能**零数据装载、零窗口、零入口** | 中 |
| **2.（可选）重功能进程隔离** | 若未来出现重型功能（内嵌浏览器等），该功能单独走子进程 + IPC | 彻底释放内存 | 视功能而定 |
| ~~3.~~ ~~ALC 卸载~~ | ~~collectible AssemblyLoadContext~~ | — | **不建议**：WPF UI 程序集卸载可靠性差，且模块代码量小，收益趋近于零 |

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 数据迁移破坏用户现有 notes.json | 拆分逻辑只读旧文件 → 写新文件成功后旧文件改名保留；`.bak` 机制沿用 |
| 全局置顶/全部显示/全局热键等跨模块逻辑遗漏禁用模块 | 这些统一收口到 `IFeatureContext.RegisterTopmostTarget` 等注册机制，模块停用时注销 |
| 单实例互斥、托盘生命周期与模块交互复杂化 | 托盘/热键/单实例全部留在宿主内核，模块不感知 |
| Trimmed 发布 + 反射组装 UI | 扩展点全部走强类型接口注册，不用反射发现；模块类硬引用，剪裁安全 |
| 用户误关功能以为数据丢了 | 禁用确认弹窗明示"数据将保留，可随时重新开启" |

---

## 7. 验收指标

- 全功能禁用（仅宿主）时：私有内存增量相对现版本下降 ≥ 50%，常驻定时器 = 0；
- 任一功能禁用后：其数据文件不读取（可用 ProcMon/日志验证）、窗口数 = 0、托盘/导航无残留入口；
- 启用 → 禁用 → 再启用往返，数据无损；
- 便利贴/任务清单各自启用禁用互不影响（延续"独立默认外观/搜索/排序"的产品理念）。
